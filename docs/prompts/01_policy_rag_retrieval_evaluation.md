# 01 — Policy RAG: Retrieval Evaluation & Improvement

Incremental build plan for improving retrieval quality of the policy documents
RAG pipeline, measured against a golden dataset at every step.

## Context (current state)

| Layer | Object | Notes |
|---|---|---|
| Bronze | `RENTAL_OPS.BRONZE.bronze_policy_documents` | 6 markdown docs, 1 row per doc |
| Silver | `RENTAL_OPS.SILVER.policy_document_chunks` | 35 header-split chunks, <=512 tokens, metadata-only Overview chunks dropped |
| Gold | `RENTAL_OPS.GOLD.policy_document_chunks` | Dynamic table (3 min lag, incremental) |
| Gold | `RENTAL_OPS.GOLD.policy_search` | Cortex Search, hybrid (text + user-provided `AI_EMBED` vectors), filter attr `document_type`, lag 1 day |

Known failure that motivates this work: *"What happens if I return the car more
than an hour late?"* does not retrieve `rental_agreement_terms_03` (the
"59 minutes past the agreed return time" rule) in the top 10. This is a
vocabulary mismatch between user phrasing and policy wording.

## Conventions for every step

- SQL lives in `src/` (pipeline objects) or `evaluation/` (eval objects, scripts, runs).
- Eval objects live in schema `RENTAL_OPS.EVALUATION`.
- Scripts are rerunnable (`CREATE OR REPLACE` / `IF NOT EXISTS`), headed with the
  same comment block style as the existing layer scripts.
- Every eval run is tagged with a `setup_version` so runs are comparable:
  `v0_baseline`, `v1_doc2query`, `v2_query_rewrite`.
- Each step ends at a commit point; nothing from a later step is built early.

## Sequence

| Step | Deliverable | Commit point |
|---|---|---|
| 1 | Baseline search service (already built) | Commit current `src/` scripts |
| 2 | Golden dataset + results table + eval procedure + baseline run (`v0_baseline`) | Commit `evaluation/` |
| 3 | Option A — ingestion-side question generation, service rebuild, eval run (`v1_doc2query`) | Commit `src/` + `evaluation/` |
| 4 | Option B — query-side rewrite + fusion + relevance threshold, eval run (`v2_query_rewrite`) | Commit `src/` + `evaluation/` |
| 5 | (Later) TruLens / AI Observability once the agent generates answers | — |

## Step 2 — Golden dataset, results table, baseline evaluation

```text
Build the retrieval evaluation framework for RENTAL_OPS.GOLD.policy_search and
run the baseline. Put all files in /evaluation (create it), numbered in run order.
Create objects in schema RENTAL_OPS.EVALUATION.

1. Golden dataset table: RENTAL_OPS.EVALUATION.policy_golden_questions
   Columns: question_id, question, question_style
   ('direct' | 'paraphrase' | 'casual' | 'out_of_scope'), is_answerable,
   expected_document_id, expected_section_header, expected_chunk_ids (ARRAY),
   notes, dataset_version, created_at.
   - Draft ~20 questions: every document covered, at least 1/3 casual or
     paraphrased user wording (include "What happens if I return the car more
     than an hour late?"), and 3-4 out-of-scope questions with no answer in the
     corpus (expected_chunk_ids empty).
   - Write the questions yourself from reading the source documents in bronze,
     NOT from chunk text generated by any model, so the set stays independent of
     Option A.
   - Label by document + section as well as chunk_id, so labels survive re-chunking.
   - Show me the draft questions and labels for review BEFORE inserting.

2. Results table: RENTAL_OPS.EVALUATION.policy_retrieval_results
   One row per (run, question): run_id, setup_version, run_ts, question_id,
   top_k, retrieved_chunk_ids (ARRAY, ranked), scores (VARIANT, the @scores per
   result), first_hit_rank, hit_at_1, hit_at_3, hit_at_5, reciprocal_rank,
   precision_at_3, recall_at_5, top_reranker_score, correctly_rejected
   (out-of-scope only), raw_response (VARIANT).

3. Summary view: RENTAL_OPS.EVALUATION.policy_retrieval_summary
   Per run_id / setup_version: hit@1, hit@3, hit@5, MRR, precision@3,
   recall@5, out-of-scope rejection rate, plus the same metrics split by
   question_style.

4. Eval procedure: RENTAL_OPS.EVALUATION.run_policy_retrieval_eval(setup_version, top_k)
   Loops over the golden set, calls SEARCH_PREVIEW per question (it requires a
   constant request, so build the JSON and use dynamic SQL), computes the
   metrics, inserts into the results table, returns the run_id. Design it so
   Step 4 can point it at a different retrieval function without rewriting the
   metric logic.

5. Run it with setup_version = 'v0_baseline', top_k = 5. Report the summary,
   list every failed question with where the expected chunk actually ranked,
   and report the reranker score distribution for answerable vs out-of-scope
   questions (this calibrates the Step 4 threshold).
```

## Step 3 — Option A: ingestion-side question generation (doc2query)

```text
Implement Option A to close the vocabulary gap at ingestion, then evaluate it
against the baseline.

1. In the Silver chunk script, generate 3-5 natural customer questions per chunk
   with AI_COMPLETE (questions the chunk answers, in casual everyday wording,
   including synonyms like "late", "overdue", "extra charge"). Store them in a
   new column (e.g. generated_questions ARRAY). Keep AI calls in Silver only so
   Gold refreshes stay free of AI cost. Use a fixed model and prompt, and
   record the model name in a column.

2. Build the indexed text as title | section + chunk text + generated questions.
   Keep chunk_text unchanged for display and citation.

3. Carry the new column(s) through the Gold dynamic table, rebuild
   policy_search, and keep change tracking working (CREATE OR REPLACE on Silver
   resets it). Keep the token budget: confirm the indexed text per chunk still
   fits the embedding model limit.

4. Show me a sample of generated questions for 5 chunks before running the eval.

5. Run the eval with setup_version = 'v1_doc2query', top_k = 5. Compare against
   v0_baseline: metric deltas overall and per question_style, questions that
   flipped pass->fail or fail->pass, and the late-return question's rank. Flag
   any leakage, i.e. generated questions that are near-copies of golden questions.
```

## Step 4 — Option B: query-side rewrite, fusion, relevance threshold

```text
Implement Option B as a retrieval layer on top of the v1 service, then evaluate it.

1. Create RENTAL_OPS.GOLD.policy_search_retrieve(question STRING, top_k INT)
   returning a structured result (VARIANT/JSON):
   - Rewrite the question into 2-3 policy-style queries with AI_COMPLETE
     (fixed model + prompt), keeping the original query as one of them.
   - Run each against policy_search, fuse the lists with reciprocal rank fusion,
     de-duplicate by chunk_id.
   - Apply a reranker-score threshold calibrated from the v0/v1 results
     (answerable vs out-of-scope distributions). If nothing passes, return an
     explicit "no relevant policy found" status instead of weak results.
   - Return citation fields per result: chunk_id, document_id, document_title,
     section_header, document_type, chunk_text, scores, plus the rewritten queries.
   - Support the optional document_type filter.

2. Extend the eval procedure to run against policy_search_retrieve (no changes
   to the metric logic), and record rewrite latency and LLM call count per question.

3. Run with setup_version = 'v2_query_rewrite', top_k = 5. Compare v0 / v1 / v2:
   metrics, out-of-scope rejection rate, added latency and cost per question,
   and whether the threshold rejects any answerable questions. Recommend whether
   the agent should call the procedure or the raw service.
```
